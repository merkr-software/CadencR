The terminal in CadencR is here for the moments when a task needs a command, a log, a manual check, or a small amount of direct work from you. It is useful. It is powerful. It is also **not** the only way to get work done.

<DocCallout title="Good to know" variant="tip">
  You do **not** need to become a terminal-heavy user to use CadencR well. The terminal is a helper,
  not the center of the workflow.
</DocCallout>

## What the terminal is doing here

Inside a feature workspace, the terminal gives you a built-in place to run commands without leaving the work you are already doing.

That matters because sometimes the fastest path is not another chat message. Sometimes you want to:

- run the exact command the agent suggested,
- read logs with your own eyes,
- check whether something actually works, or
- do a quick little human cleanup before moving on.

Think of it as the **manual override**. Most of the time, the agent and editor do the heavy lifting. The terminal is there for the practical finishing moves.

## When to use it

These are the most common “yep, terminal time” moments:

| Use the terminal when you want to... | Why it helps                                                                   |
| ------------------------------------ | ------------------------------------------------------------------------------ |
| Run a command the agent recommended  | You can verify the result yourself instead of relying only on a summary        |
| Read logs or error output            | Raw output is often clearer than a paraphrase                                  |
| Do a manual check                    | Great for quick “does this build / start / pass?” moments                      |
| Start a local tool or dev server     | Handy when a task needs something running beside the agent                     |
| Make a tiny one-off change yourself  | Sometimes typing one command is faster than describing it three different ways |

A good rule of thumb: if the task involves **commands, output, or verification**, the terminal is probably the right tool.

## Controls that pay for themselves quickly

The terminal has its own small keyboard scope inside a feature workspace:

| Shortcut                     | What it does                         |
| ---------------------------- | ------------------------------------ |
| <kbd>⌘ T</kbd>               | Focus or open the terminal           |
| <kbd>⌘ D</kbd>               | Split horizontally                   |
| <kbd>⌘ <ShiftIcon /> D</kbd> | Split vertically                     |
| <kbd>⌘ ⌥</kbd> + arrows      | Focus the neighbouring terminal pane |
| <kbd>⌘ W</kbd>               | Close the focused pane               |

<DocCallout title="Heads up: opposite of the editor" variant="note">
  In the terminal, <kbd>⌘ D</kbd> splits **horizontally** and{" "}
  <kbd>
    ⌘ <ShiftIcon /> D
  </kbd>{" "}
  splits **vertically**. In the editor, those two are reversed. The defaults match what most people
  reach for first in each surface.
</DocCallout>

### Working directory awareness

Each terminal pane is launched in the feature's worktree. If something inside the shell drifts the cwd elsewhere (for example, a misbehaving `cd` in a script), CadencR shows a small cwd warning so you do not accidentally run commands against the wrong checkout.

## When not to use it

The terminal is helpful, but it does not need to become your default answer to everything with a pulse.

You can usually skip it when:

- the agent can handle the step just fine on its own,
- the editor already shows you what you need,
- you are about to paste a command you do not understand at all,
- you are only opening it because terminals seem like what “real developers” do.

That last one is especially unnecessary. Plenty of good developers use the terminal only when it is the clearest tool for the job.

## Good habits and small confidence tips

If you are terminal-curious but terminal-cautious, these habits help a lot:

1. **Start with read-only checks.** Things like listing files, printing the current folder, or reading output feel much safer than change-making commands.
2. **Run one thing at a time.** You do not need to learn everything at once.
3. **Read before pressing Enter.** Even a five-second pause counts as wisdom.
4. **Ask the agent to explain a command in plain English.** “What will this do?” is a very good question.
5. **Use it for confidence, not performance.** The goal is not to look advanced. The goal is to understand what is happening.

<DocCallout title="A surprisingly strong move" variant="note">
  If a command looks unclear, ask the agent to break it into parts before you run it.
</DocCallout>
