CadencR runs agent CLIs installed on your host. Built-in integrations support **Claude Code, Codex, and OpenCode**. **Cursor** is available as an official provider plugin from the marketplace. You can also create or import a local **ACP** connector.

## Set up a built-in provider

1. Install and authenticate its native CLI using that provider's own workflow.
2. Open **Settings → Providers**.
3. Check discovery, binary selection, and any reported setup error.
4. Choose a discovered model in a conversation.
5. Review the thinking, collaboration, access, and profile controls the runtime actually exposes.

Unavailable local providers are not selectable. A moved or upgraded OpenCode installation can be rediscovered when its saved executable becomes stale. Errors in discovery or persistence are visible.

## Install the Cursor plugin

Cursor is no longer built in. It runs through an official provider plugin, a connector that CadencR installs like any other marketplace provider.

1. Install the Cursor CLI: `curl https://cursor.com/install -fsS | bash`.
2. Authenticate it with `agent login`.
3. Install **Cursor** from the marketplace's **Providers** section, then restart CadencR when prompted.
4. Choose a Cursor model in a conversation.

Settings has no Cursor tab, and the plugin finds the `agent` CLI itself. Cursor's access mode (Default, Full Access, or Auto Review) is a setting of each conversation in its session configuration. It is not a workspace default. Existing Cursor conversations keep their provider and can continue once the plugin is installed.

## Controls are capability-based

Models, thinking levels, modes, permission options, attachments, context usage, and resume support vary by provider. CadencR displays supported controls through a shared interface; it does not invent missing ACP information.

The Cursor plugin does not report authoritative context usage and exposes limited live sub-agent detail. Its structured questions and plan approval are available when Cursor emits them; some models or turns may not. CadencR's `/compact` action is not available for Cursor. Any plugin or local connector only exposes the capabilities it implements and negotiates.

## Provider and model selection

New conversations inherit the provider and model from the last accepted manual prompt across projects. Explicit conversation overrides take priority. Model favorites are provider-aware and shared across the workspace.

Thinking choices resolve against the selected model and profile. Switching to a model without the previous option clears it instead of sending an invalid configuration. Supported Codex models expose persistent Fast mode using the priority service tier.

## Named profiles

Provider profiles select provider-specific configuration. Claude profile changes for new conversations do not replace the profile already used by an existing one.

Codex supports named profiles with optional native **`config.toml`** and environment overrides. Manage profiles and the default in CLI Providers, then select a supported conversation override in **Info**. Model catalogs and runtime controls follow the selected profile. Explicit profile choices are respected when applying defaults such as thinking or reasoning-summary behavior.

CadencR does not collect or broker the account credentials of a local connector. Authenticate its native agent first.

## Create a local ACP connector

Use the provider-development action to create a connector project. It contains **README.md** and **INSTRUCTION.md** describing the executable, model-discovery, ACP v1, validation, and lifecycle contract.

Ask an agent to read those instructions and implement the connector. The generated project is a scaffold, not an already working provider. Build it at the required stable output, normally `bin/provider` or `bin/provider.exe` on Windows.

Restart CadencR after connector or registration changes. Then choose its discovered models in a normal conversation and verify the session controls and resume behavior it advertises.

## Import an existing connector

Import an existing **Git repository** whose connector is already built at the required path. The host validates the executable and discovers its models. Importing source alone does not build the connector for you.

Local connector projects and their registrations are distinct from signed published packages. To distribute a connector, prepare its platform bundles, publish an author GitHub release, and submit a registry PR. Follow [Publish to the marketplace](../marketplace-publishing/); a generated project alone is not publicly installable.
