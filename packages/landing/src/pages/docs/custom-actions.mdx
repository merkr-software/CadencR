Custom actions are **shell commands** you attach to a project. The `+` button in a feature header opens the menu of actions defined for the current project (plus any global ones), and you can either run an action right now or have it run automatically on an interval. Every action gets the same buttons on every feature of the project, but its variables and schedule are tracked **per feature**.

## What a custom action actually is

Each action stores:

- a **name** and icon you will see in the menu,
- a **command** — the literal shell line that will be executed,
- a **scope** — `Project` (visible only on features of that project) or `Global` (visible everywhere),
- a list of **variable names** parsed from the command, and
- a position so you can reorder them in the menu.

The command is run with a hard **5-minute timeout** on the host machine. The working directory is the feature's worktree (so anything `cd`-relative starts from the right place automatically). When you want to watch output live, run the action in a terminal split instead of only reading the status dot afterward.

## Variables

Anywhere in the command, write `${VAR_NAME}` and Cadencr treats `VAR_NAME` as a variable. Names must be uppercase letters, digits, or underscores and start with a letter or underscore. The set of placeholders is discovered automatically — there is nothing to declare on the side.

Example commands:

```sh
gh pr view ${PR_ID}
npm run check --workspace=${PACKAGE}
echo "Hi ${NAME}, the worktree is $(pwd)"
```

Values are stored **per (action, feature)**, so the same "Run tests" action can have `PACKAGE=desktop` on one feature and `PACKAGE=service` on another. The action will refuse to run if a referenced variable has no value for the current feature — you fill them in once and the value sticks until you change it.

There are no implicit variables. If you want the feature path or branch name in your command, use the worktree-relative cwd (the action already runs there) or pipe through `git`, e.g. `git rev-parse --abbrev-ref HEAD`.

## Schedules

Every action can be scheduled to run automatically on the current feature. The schedule control is a switch plus an interval (seconds / minutes / hours), with a minimum of **5 seconds**:

| Trigger      | When it fires                                                                                            |
| ------------ | -------------------------------------------------------------------------------------------------------- |
| **Manual**   | You click the action in the menu (or run it from the header), optionally opening it in a terminal split. |
| **Schedule** | A fixed-interval tokio task fires it on the feature in the background, as long as the switch is on.      |

Schedules are not cron — they are pure fixed intervals starting from when you enable them. Saving a new interval cancels the previous task and starts fresh, so you can change the cadence safely while the action is enabled. Like variables, the schedule is tracked per `(action, feature)` — the same action can poll every 30 s on one feature and stay off on another.

## Status dot

Each action shows a small status dot you can read at a glance:

| Dot           | Meaning                                                                   |
| ------------- | ------------------------------------------------------------------------- |
| Grey          | Never run on this feature yet.                                            |
| Pulsing amber | A run is in progress (manual or scheduled — Cadencr does not care which). |
| Green         | Last run exited 0.                                                        |
| Red           | Last run exited non-zero. Hover for the exit code.                        |

## Good action shapes

Custom actions are most useful for **short, repeatable shell jobs** that you do not want to retype:

- run a targeted test command on the current feature,
- poll a CI run or PR status with `gh`,
- regenerate a small artifact (`pnpm generate:api`, `cargo sqlx prepare`, …),
- push a quick metric to a dashboard,
- ping a deploy that should track this feature's branch.

If the action is really a one-shot "do this thing once" prompt for the agent, that is what the prompt bar is for — keep custom actions for genuine shell work.

## Editor dialog

The action editor dialog lets you:

- create or rename an action and pick its icon,
- pin it to the toolbar (so the top header gets a one-click button) or leave it in the overflow menu,
- edit the command template — variable names show up as you type,
- delete it.

Per-feature variable values and the schedule live next to the action button on each feature, not inside the editor dialog — so a project owner can tweak the command in one place without overwriting everyone's variable values.

When you have more actions than the toolbar can fit, the overflow dropdown keeps the rest one click away.
