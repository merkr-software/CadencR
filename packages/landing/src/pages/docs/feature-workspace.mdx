A feature workspace is the main place where you do one piece of work in Cadencr. If a task needs agent help, file edits, terminal commands, and a quick Git confidence check, this is where those things live together instead of being scattered across separate windows.

<DocCallout title="Quick translation" variant="tip">
  In Cadencr, a “feature” does **not** have to mean something fancy. It can be a bug fix, docs
  update, refactor, cleanup, or any other focused task.
</DocCallout>

## What a feature workspace is

Think of a feature workspace as a **home base for one job**.

It gives you a single, focused space for:

- the agent session doing the work,
- the files you want to inspect or edit,
- the browser for live previews, docs, or visual feedback,
- the terminal for commands that need a human touch, and
- the Git view for checking what changed before you call it done.

The big mental model is simple: **one workspace = one piece of work**. That makes it easier to stay organized, easier to review changes, and much easier to come back later without asking yourself, “Wait, which tab was the important one again?”

## What you’ll usually see there

The exact layout can change a bit, but these are the usual suspects:

| Area               | What it is for                                                       | When to use it                                                           |
| ------------------ | -------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Agent/session area | Chatting with the agent and following its progress                   | When you want to ask for work, steer it, or review what it is doing      |
| Editor             | Opening files, reading code, checking diffs, and making manual edits | When you want to verify something with your own eyes or tweak the result |
| Terminal           | Running commands inside the feature’s working context                | When the task needs tests, tooling, or direct command-line work          |
| Git view           | Seeing changed files and checking your work before the next step     | When you want the “okay, what actually changed?” view                    |

You may see these as tabs, panes, or both. That is normal. The workspace is meant to help you move between thinking, checking, editing, and verifying without losing the thread.

The main panes have one-stroke keyboard switches: <kbd>⌘ <ShiftIcon /> A</kbd> for Agent, <kbd>⌘ <ShiftIcon /> E</kbd> for Editor, <kbd>⌘ <ShiftIcon /> T</kbd> for Terminal, and <kbd>⌘ <ShiftIcon /> G</kbd> for Git. Open the Browser tab when you need a live page or want to send page context back to the agent.

### The feature header

Above the panes you get a handful of header controls that are easy to miss:

- **Feature label** — <kbd>⌘ <ShiftIcon /> L</kbd> to rename inline.
- **Feature settings popover** — <kbd>⌘ <ShiftIcon /> P</kbd> (or <kbd>⌥ P</kbd>) for the per-feature options (provider profile, model defaults, working directory, …).
- **Custom actions bar** — your saved actions live here; the `+` opens the action menu. See [Custom actions](../custom-actions/).
- **Git actions** — <kbd>⌘ G</kbd> opens the popover with commit / push / compare; the branch picker is <kbd>⌘ B</kbd>.
- **Archive** — <kbd>⌘ <ShiftIcon /> X</kbd> archives the feature (or permanently deletes it when run on an already-archived one). Archived features stay searchable from the sidebar; they are not destroyed on first press. When terminals are still running, the archive / delete dialogs can also kill those terminals.

## A good way to work inside it

A simple rhythm works well for most people:

1. **Start with the task.** Open or create the feature workspace for the thing you want to finish.
2. **Use the agent to get moving.** Ask for the first draft, investigation, or implementation pass.
3. **Check the editor.** Open the files the agent touched so you can confirm they make sense in plain human language.
4. **Use the terminal only when it helps.** Run tests, inspect output, or do quick project tasks when needed.
5. **Finish with Git.** Before you call the work done, check the changed files so nothing surprising slipped in.

If you are newer to development, this flow is especially helpful because it keeps every step visible. You do not need to “just know” what is happening — the workspace is built so you can inspect the work as you go.

## Common mistakes to avoid

- **Putting unrelated tasks in one feature workspace.** If the work is really a different job, give it a different home base.
- **Staying only in the chat.** The agent is helpful, but the editor and Git view are where confidence comes from.
- **Using the terminal as a first resort.** It is there to help, not to intimidate. If the agent or editor answers the question, start there.
- **Skipping the final Git check.** This is how tiny surprises become medium-sized surprises.

<DocCallout title="A good rule of thumb" variant="note">
  If the workspace starts to feel messy, that is usually a sign the task is too broad, not that you
  are doing something wrong.
</DocCallout>
