A **worktree** is a checked-out copy of your repository on its own branch, living in its own folder. Cadencr leans on worktrees so several features — and several agents — can work in parallel without overwriting each other's files.

## Why Cadencr uses worktrees

If two agents are editing the same checkout at once, you get one of two outcomes: a corrupted working tree, or both agents fighting over the same files. Neither is fun. Worktrees give every feature its own isolated playground:

- the agent has a clean directory it can change freely,
- you can run tests or builds against one feature without affecting the others,
- switching features no longer means a `git stash` dance,
- archiving or deleting a feature is just cleaning up its worktree.

<DocCallout title="One-line mental model" variant="tip">
  Feature = a focused unit of work. Worktree = the folder on disk where that work happens.
</DocCallout>

## How worktrees show up in the UI

You will rarely have to think about them, but a few places make the worktree explicit:

- **Command palette** (<kbd>⌘ K</kbd>) — when you start a new feature, the worktree step lets you pick an existing worktree, create a fresh worktree on a new branch, or choose the explicit branch/worktree mode that matches the task.
- **Git tab** — the branch displayed is the branch of the current feature's worktree. The diff is against that worktree's target branch.
- **Terminal** — every pane starts inside the feature's worktree folder. The cwd warning appears if something drifts elsewhere.
- **Editor** — the file tree is rooted at the worktree.
- **Sidebar status** — setup output and deferred branch-switch messages stay visible so you can see whether the feature is ready before the first prompt runs.

## When to reuse vs create

You usually want a **new worktree** when:

- you are starting a new feature, fix, or refactor,
- you want a clean branch for the agent to work on,
- you might want to compare results from several attempts side by side,
- you are tempted to reuse the project's main working tree. Cadencr avoids using the main checkout as a feature worktree because it is too easy to overwrite unrelated local work.

You usually want to **reuse an existing worktree** when:

- you are continuing yesterday's work on the same branch,
- the feature is mid-review and you do not want to start a new branch,
- you deliberately picked an existing worktree and understand what else is already in it.

## Branch switching notes

If a feature has not sent its first prompt yet, Cadencr may defer a branch switch until that first message starts the worktree setup. The UI surfaces that state instead of pretending the branch moved immediately. Once the worktree exists, the Git tab, Editor, Terminal, and Browser all stay tied to that feature's folder.

## Cleaning up

Archiving a feature (<kbd>⌘ <ShiftIcon /> X</kbd>) leaves its worktree alone by default. If you archive an already-archived feature, Cadencr removes the worktree from disk and prunes it from Git. That two-step is intentional — it is hard to lose work by accident.
