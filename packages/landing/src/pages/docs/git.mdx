In CadencR, Git is visible because it helps you stay oriented: what changed, where those changes live, and what to do next.

## Why Git appears so much in CadencR

CadencR is built around **feature-based work**. Each feature gets its own working area — usually a Git **worktree** on its own branch — so several features can move at the same time without stepping on each other's commits.

Why do that? Because it keeps work tidy:

- one feature does not casually spill into another,
- agent changes stay reviewable,
- you can check what happened before you commit to it, and
- opening a pull request back into the target branch feels deliberate and easier to review.

A few Git concepts show up directly in the CadencR interface:

| Term     | Plain-English version                                               | Why you care in CadencR                                                |
| -------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Branch   | A separate lane for one piece of work                               | Each feature can stay focused instead of tangling with everything else |
| Worktree | A checked-out copy of the repo on its own branch, in its own folder | Lets several features (and agents) work in parallel without conflicts  |
| Commit   | A saved checkpoint with a message                                   | It is the moment you say, “Yes, this set of changes belongs together”  |
| Diff     | The before/after view of a change                                   | This is how you check what really changed, not what you hope changed   |
| Push     | Sending your branch to the remote repo                              | Useful when you want to share or open a PR                             |
| Compare  | Opening a comparison or pull request against the target branch      | The “okay, this lane is ready for review” step                         |

<DocCallout title="Gentle truth" variant="tip">
  In CadencR, Git is mainly there to answer practical questions: what changed, what branch this work
  belongs to, and what the next step should be.
</DocCallout>

## What the Git tab helps you do

The Git tab is the calm, visual version of “so... what happened here?”

  caption="A friendly place to review changed files, compare against the target branch, and decide whether the next step is commit, push, or compare."
  bordered={false}

Inside the Git tab, CadencR helps you:

- review changed files before you trust them,
- switch between **uncommitted changes** and **changes vs the target branch**,
- inspect the diff instead of guessing,
- switch to the commit graph when you need history, branch shape, or a commit-level diff,
- see what branch you are on and what it is compared against,
- reach the header actions for the next sensible step: **Commit** (<kbd>⌘<ShiftIcon />K</kbd>), **Push** (<kbd>⌘<ShiftIcon />U</kbd>), and **Open compare / PR** (<kbd>⌘<ShiftIcon />O</kbd>), or the <kbd>⌘G</kbd> popover for everything else.

The branch picker lives behind <kbd>⌘B</kbd> while a feature is focused, so swapping branches inside a worktree never needs a mouse trip.

### Commit graph

The Git tab also includes a commit graph view. Use it when the question is about history rather than uncommitted files: which branch contains a commit, how your branch diverged from the target, or what changed in a specific commit. When a remote URL is available, CadencR can also open the matching online commit or comparison view.

### Reviewing the diff with the keyboard

The diff viewer is built for keyboard-driven review:

| Shortcut                              | What it does                 |
| ------------------------------------- | ---------------------------- |
| <kbd>Ctrl J</kbd> / <kbd>Ctrl K</kbd> | Next / previous file         |
| <kbd>Ctrl L</kbd>                     | Toggle the focused file      |
| <kbd>Ctrl D</kbd> / <kbd>Ctrl U</kbd> | Scroll half a page down / up |
| <kbd>Ctrl H</kbd>                     | Mark file viewed / unviewed  |
| <kbd>⌘ Enter</kbd>                    | Send pending review comments |

If you prefer to drive review from the unified agent list or session view, the same shortcuts apply once the diff has focus.

## Safe everyday Git workflow in CadencR

If you want the least dramatic daily rhythm, this is a good one:

1. **Start work in a feature workspace.** Think “one task, one home base.”
2. **Let the agent work, or make edits yourself.** No Git action needed yet.
3. **Open the Git tab and review the diff.** This is your confidence step.
4. **Commit when the change makes sense as one unit.** A commit is just a checkpoint with a label.
5. **Push when you want the branch on the remote.** Helpful for sharing, backup, or opening a PR.
6. **Open compare / PR when the feature is actually ready.** CadencR will surface the comparison against the target branch and, when configured, hand off to your forge for the actual PR.

A simple mental model helps here:

- **Git tab** = review and understand
- **Commit** = save this chunk of work
- **Push** = share this branch with the remote repo
- **Compare / PR** = hand the finished work back to the target branch for review

### Worktrees in one paragraph

When you start a feature, CadencR can spin up a Git worktree for it — a real folder on disk on its own branch, separate from your main checkout. That is what lets several agents run in parallel without overwriting each other's files. The command palette's worktree picker (<kbd>⌘K</kbd>) is where you choose to reuse an existing worktree or create a new one; the rest of the time, the Git tab simply reflects the worktree the current feature is in.

If your team cares about merge style, CadencR has a **Git merge strategy** setting. If your team does **not** care, leaving the default alone is a completely respectable life choice.

<DocCallout title="Beginner-friendly rule" variant="note">
  If you are unsure what to do next, open the Git tab before opening a terminal. A visible diff is
  usually more helpful than jumping straight into terminal commands.
</DocCallout>
