The first commit on CadencR landed on February 11th. Today, 1,824 commits later, the whole thing is on [GitHub](https://github.com/merkr-software/cadencr) under Apache 2.0. Free. No paid tier, no "pro" plan, no waitlist.

If you want to skip the rest, [grab the latest release](https://github.com/merkr-software/cadencr/releases/latest). macOS, Windows, Linux.

## Why give it away

Honestly, this wasn't the plan. I started CadencR as a personal tool, for me. The CLI agents I was using were powerful but the workflow around them drove me up a wall, so I built the thing I wished existed and used it every day. It was never meant to leave my laptop.

What actually changed my mind happened by accident. People would glance at my screen while I was working, slow down, and then start asking questions. "Wait, what is that?" "Are those all running at the same time?" "What's that panel on the side?" It kept happening. Not from people I'd shown the tool to, from people who just happened to look over and got curious.

That's a hard signal to ignore. At that point keeping it to myself felt selfish, and selling it felt worse. The IDE is the most intimate piece of software a developer touches; it sees every keystroke, every prompt, every half-finished thought you typed and deleted. If I'm going to ask people to trust it, the least I can do is let them read the source.

The other reason is that the way developers work is being rewritten in real time, and nobody (me included) knows what the right shape is yet. I'd rather be wrong in public and fix it fast than be wrong on my own laptop forever.

## What CadencR actually does

It's a desktop IDE that runs Claude Code, OpenCode, and Codex side by side, in one window, with a real UI on top instead of a terminal scrollback.

The two things I cared most about getting right:

**Running more than one agent at a time.** If you've used a CLI agent, you've probably noticed they spend a lot of their time waiting. For you to read a diff. For a test to run. For a permission prompt. CadencR puts each session in its own Git worktree on its own feature, so while one's working you can start another. I usually have three or four going at once. It changes the job.

**Being able to read what the agent did.** There's a popular take right now that you don't really need to watch the agent anymore. For a side project, a script, a throwaway prototype, that's fair. Models have gotten genuinely good, and at small scale you can let them rip and only look at the output.

Try the same thing on a 10M-line codebase and the illusion falls apart fast. Ask an agent to find a bug somewhere in real production code and you'll watch it confidently edit the wrong file, miss the convention three modules over, or "fix" a symptom while the cause sits untouched. Fully autonomous software development is coming, probably. It's not here yet. In the meantime, the difference between an agent that helps and an agent that quietly burns an afternoon is whether a human is guiding, reviewing, and noticing things early.

That's the part a terminal scrollback is terrible at. A 4,000-line stream of tool calls is not a UI, it's a coping mechanism. CadencR renders sessions as something you can actually skim: file changes grouped, tool calls collapsed, plan and approvals as their own surfaces. The point isn't to babysit every token. It's to make spot-checking cheap enough that you'll actually do it.

Everything else (the editor, the built-in terminal, Git, custom actions, shortcuts) is there because I needed it myself while building the first two.

## Three months in

A few numbers, because they're more honest than adjectives:

- 1,824 commits
- 14 docs pages
- Three supported agents (Claude Code, OpenCode, Codex)
- Zero analytics calls home

## What to do next

[Download it](https://github.com/merkr-software/cadencr/releases/latest), or [read the source](https://github.com/merkr-software/cadencr) if you want to see how the sausage gets made. The [Concept doc](/docs/concept/) is probably the best starting point if you want the longer version of the pitch.

A fair warning: this is a first version of a three-month-old project, and plenty is still rough. The next focus is performance and stability. Faster cold starts, fewer surprises, less jank in the places you live in every day. The work ahead is tracked in [GitHub issues](https://github.com/merkr-software/cadencr/issues), and I read every one. If something annoys you, that's the bug. Open one.

If you build something with it, or against it, I'd love to know.
